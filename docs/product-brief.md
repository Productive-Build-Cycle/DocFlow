## 1. Project Overview

### 1.1. Project Objective

هدف این پروژه، طراحی و پیاده‌سازی یک سامانه متمرکز مدیریت اسناد سازمانی (Document Management System) است که امکان ذخیره‌سازی، دسته‌بندی، مدیریت، جستجو، کنترل نسخه‌ها، بررسی، تأیید، انتشار و آرشیو اسناد را برای واحدهای مختلف سازمان فراهم کند.

در این راهکار، یک زیرساخت متمرکز ذخیره‌سازی روی سرورهای اختصاصی سازمان ایجاد می‌شود و واحدهای مختلف می‌توانند از طریق یک سامانه تحت وب، اسناد خود را بارگذاری و مدیریت کنند.

هر سند علاوه بر فایل اصلی، دارای اطلاعات ساختاریافته (Metadata) خواهد بود؛ از جمله:

- **Document Code:** کد یا شماره شناسایی سند
- **Document Title:** عنوان سند
- **Document Type:** نوع سند
- **Department:** واحد سازمانی مرتبط
- **Owner:** مالک یا مسئول سند
- **Project:** پروژه مرتبط
- **Version:** شماره نسخه
- **Status:** وضعیت فعلی سند
- **Creation Date:** تاریخ ایجاد
- **Last Modified Date:** آخرین تاریخ تغییر
- **Approval Information:** اطلاعات مربوط به بررسی و تأیید

سامانه باید علاوه بر نگهداری فایل‌ها، چرخه عمر هر سند (Document Lifecycle) را از زمان ایجاد تا بررسی، تأیید، انتشار، اصلاح و آرشیو مدیریت کند.

### 1.2. Vision

هدف نهایی، ایجاد یک مرجع رسمی، متمرکز و قابل اتکا برای اسناد سازمان است؛ به‌گونه‌ای که در هر لحظه بتوان مشخص کرد:

- هر سند متعلق به کدام واحد سازمانی است؟
- چه کسی مسئول نگهداری و به‌روزرسانی آن است؟
- آخرین نسخه معتبر سند کدام است؟
- سند در چه مرحله‌ای از گردش کار قرار دارد؟
- چه افرادی مجاز به مشاهده یا ویرایش آن هستند؟
- چه تغییراتی در طول زمان روی سند انجام شده است؟

**اصل کلیدی پروژه:**

هدف صرفاً ایجاد یک فضای ذخیره‌سازی فایل روی سرور نیست؛ بلکه ایجاد یک بستر سازمانی برای مدیریت اسناد و کنترل کامل چرخه عمر آن‌ها (Document Lifecycle Management) است.

## 2. Problem Statement

### 2.1. Current Situation

در حال حاضر، سازمان اسناد خود را عمدتاً در تعدادی File Sharing و Shared Folder نگهداری می‌کند.

این ساختار امکان ذخیره‌سازی و اشتراک‌گذاری فایل‌ها را فراهم می‌کند، اما به‌تنهایی پاسخگوی نیازهای سازمان در زمینه مدیریت رسمی اسناد نیست.

مسئله اصلی این است که سازمان محل‌هایی برای ذخیره‌سازی فایل‌ها در اختیار دارد، اما از یک سیستم یکپارچه برای مدیریت چرخه عمر اسناد برخوردار نیست.

### 2.2. Current Challenges

چالش‌های اصلی وضعیت موجود عبارت‌اند از:

| حوزه | مشکل موجود |
|---|---|
| Central Repository | پراکندگی اسناد در محل‌های مختلف |
| Version Control | نبود سازوکار استاندارد و متمرکز برای مدیریت نسخه‌ها |
| Approval | نبود فرایند رسمی و قابل پیگیری برای تأیید اسناد |
| Rejection / Return | نبود سازوکار مشخص برای رد یا بازگرداندن اسناد جهت اصلاح |
| Workflow | مشخص نبودن مسیر گردش اسناد بین کاربران و واحدها |
| Document Status | نبود امکان مشاهده وضعیت جاری سند |
| Audit Trail | ثبت نشدن کامل و متمرکز تاریخچه اقدامات کاربران |
| Document Ownership | مشخص نبودن مسئول رسمی هر سند |
| Latest Valid Version | دشواری تشخیص آخرین نسخه معتبر و قابل استفاده |
| Search | محدود بودن جستجو به نام فایل و ساختار پوشه‌ها |
| Access Control | محدود بودن کنترل دسترسی به سطح پوشه |
| Reporting | محدودیت در گزارش‌گیری از وضعیت و عملکرد اسناد |
| AI Readiness | نبود ساختار مناسب برای استفاده هوشمند از محتوای اسناد |

### 2.3. Real Business Scenario

فرض کنیم یک دستورالعمل مونتاژ (Work Instruction) در خط تولید تغییر می‌کند.

در ساختار فعلی ممکن است پاسخ به سؤالات زیر دشوار یا غیرممکن باشد:

- چه کسی سند را تغییر داده است؟
- دلیل تغییر چه بوده است؟
- نسخه قبلی و نسخه جدید چه تفاوتی دارند؟
- چه کسی باید سند را بررسی کند؟
- چه کسی مسئول تأیید نهایی است؟
- آیا نسخه جدید تأیید و منتشر شده است؟
- آیا نسخه قبلی از اعتبار استفاده جاری خارج شده است؟
- آیا کاربران خط تولید به آخرین نسخه معتبر دسترسی دارند؟

بنابراین مسئله اصلی صرفاً مدیریت فایل نیست؛ بلکه نبود کنترل، شفافیت و قابلیت پیگیری در کل چرخه عمر اسناد سازمان است.

## 3. Target Users & Roles

کاربران هدف سامانه شامل تمام افرادی هستند که در سازمان با ایجاد، بررسی، تأیید، نگهداری یا استفاده از اسناد سروکار دارند.

| User / Role | مسئولیت‌ها و نیازمندی‌ها |
|---|---|
| Engineer / Document Creator | ایجاد سند، بارگذاری فایل، ثبت اطلاعات و ارسال سند برای بررسی |
| Document Controller | کنترل کد سند، Metadata، نسخه‌ها، گردش کار و انتشار |
| Reviewer | بررسی محتوای سند و ثبت نظرات و درخواست‌های اصلاحی |
| Approver / Manager | تأیید یا رد رسمی سند |
| Department Manager | مدیریت اسناد و کاربران واحد مربوطه |
| Project Manager | پیگیری وضعیت اسناد مرتبط با پروژه‌ها |
| Quality | کنترل اسناد مرتبط با کیفیت و اطمینان از اعتبار نسخه‌ها |
| Production User | مشاهده و دریافت آخرین نسخه معتبر دستورالعمل‌ها |
| System Administrator | مدیریت کاربران، نقش‌ها، دسترسی‌ها و تنظیمات سامانه |

### 3.1. Role Management Principle

نقش‌ها باید از کاربران مستقل باشند؛ به این معنی که یک کاربر بتواند به‌صورت هم‌زمان چند نقش داشته باشد.

برای مثال، یک مدیر واحد ممکن است هم‌زمان نقش‌های زیر را داشته باشد:

- Document Creator
- Reviewer
- Approver

همچنین دسترسی‌های هر نقش باید متناسب با مسئولیت آن تعریف و قابل مدیریت باشد.

### 4.1. Conceptual Data & Storage Architecture

یکی از اصول مهم طراحی سامانه، تفکیک فایل اصلی از اطلاعات مدیریتی و ساختاریافته مربوط به آن است.

این تفکیک دو بخش اصلی دارد:

**1. File Storage**

محل نگهداری فایل‌های اصلی اسناد، مانند:

- PDF
- Word
- Excel
- Images
- سایر فرمت‌های موردنیاز سازمان

**2. Database**

محل نگهداری اطلاعات مدیریتی و ساختاریافته، مانند:

- مشخصات و Metadata سند
- مالک و واحد سازمانی
- شماره و تاریخ نسخه‌ها
- وضعیت سند
- اطلاعات بررسی و تأیید
- سطوح دسترسی
- تاریخچه اقدامات کاربران

به این ترتیب، فایل‌ها در زیرساخت ذخیره‌سازی مرکزی نگهداری می‌شوند و اطلاعات مدیریتی آن‌ها در پایگاه داده ثبت خواهد شد.

این معماری امکان مدیریت مستقل فایل‌ها و اطلاعات مربوط به آن‌ها را فراهم می‌کند.

## 5. Main User Flow

جریان اصلی کار سامانه از زمان ایجاد سند تا انتشار و استفاده از آن، به شکل زیر تعریف می‌شود.

### 5.1. Document Lifecycle

**Step 1 — Create Document**

کاربر یک سند جدید ایجاد می‌کند و اطلاعات اولیه مانند کد، عنوان، واحد سازمانی و نوع سند را ثبت می‌کند.

Initial Status: `Draft`

**Step 2 — Upload File**

فایل سند بارگذاری شده و به‌عنوان نسخه اولیه در مخزن مرکزی ذخیره می‌شود.

**Step 3 — Submit for Review**

ایجادکننده، سند را برای بررسی ارسال می‌کند.

Status: `Submitted`

**Step 4 — Document Review**

Reviewer محتوای سند را بررسی می‌کند.

در صورت وجود ایراد، سند همراه با توضیحات و نظرات اصلاحی برای ایجادکننده بازگردانده می‌شود.

Possible Statuses:

- `Under Review`
- `Returned`

**Step 5 — Revision**

ایجادکننده اصلاحات موردنیاز را انجام داده و نسخه جدیدی از سند ایجاد می‌کند.

نسخه‌های قبلی باید بدون حذف و با حفظ تاریخچه در سامانه باقی بمانند.

**Step 6 — Approval**

Approver سند را بررسی کرده و در صورت تأیید، آن را تأیید نهایی می‌کند.

در صورت عدم تأیید، سند می‌تواند با ذکر دلیل رد یا برای اصلاح بازگردانده شود.

Status: `Approved` یا وضعیت متناسب با نتیجه تصمیم

**Step 7 — Publication**

نسخه تأییدشده به‌عنوان نسخه رسمی و معتبر منتشر می‌شود.

Status: `Published`

**Step 8 — Document Consumption**

کاربران مجاز سازمان، به‌ویژه کاربران واحدهای تولید و کیفیت، می‌توانند آخرین نسخه منتشرشده و معتبر را مشاهده یا دریافت کنند.

**Step 9 — Revision & Archive**

در صورت نیاز به تغییر سند، فرایند ایجاد نسخه جدید آغاز می‌شود.

پس از تأیید و انتشار نسخه جدید، نسخه قبلی از اعتبار استفاده جاری خارج شده و با حفظ تاریخچه در سامانه باقی می‌ماند.

### 5.2. Example: Work Instruction

فرض کنیم یک دستورالعمل مونتاژ صندلی خودرو در سامانه ثبت شده است.

| Property | Value |
|---|---|
| Document Code | WI-ASSY-SEAT-001 |
| Document Title | Seat Assembly Work Instruction |
| Initial Version | 1.0 |
| Initial Status | Draft |

پس از بررسی، تأیید و انتشار نسخه 1.0، این نسخه به‌عنوان نسخه معتبر سند شناخته می‌شود.

اگر مهندس تولید بخواهد دستورالعمل را اصلاح کند، نسخه 2.0 ایجاد خواهد شد.

**Business Principle:**

تا زمانی که نسخه 2.0 بررسی، تأیید و منتشر نشده است، نسخه 1.0 باید مطابق سیاست سازمان به‌عنوان آخرین نسخه معتبر قابل استفاده باقی بماند.

پس از انتشار نسخه 2.0، نسخه قبلی از اعتبار جاری خارج می‌شود؛ اما برای اهداف تاریخی، ممیزی و ردیابی همچنان در سامانه نگهداری خواهد شد.

## 6. MVP Scope

### 6.1. MVP Objective

هدف از MVP (Minimum Viable Product)، ارائه اولین نسخه قابل استفاده از سامانه است که بتواند نیازهای اصلی سازمان را در زمینه مدیریت اسناد، کنترل نسخه‌ها، مدیریت دسترسی و گردش تأیید برطرف کند.

پیشنهاد می‌شود در فاز اول، از توسعه قابلیت‌های پیچیده و پیشرفته خودداری کرده و تمرکز بر پیاده‌سازی هسته اصلی سیستم باشد.

### 6.2. Features Included in MVP

قابلیت‌های زیر برای نسخه اولیه سامانه پیشنهاد می‌شوند:

| Domain | Required Features |
|---|---|
| Authentication | ورود و احراز هویت کاربران |
| User Management | تعریف و مدیریت کاربران |
| Role Management | تعریف و مدیریت نقش‌های مختلف |
| Permission Management | کنترل دسترسی به اسناد |
| Central Repository | ایجاد مخزن متمرکز اسناد |
| File Upload / Download | بارگذاری و دریافت فایل‌ها |
| Document Management | ایجاد، ویرایش و مدیریت اطلاعات اسناد |
| Metadata | ثبت اطلاعات و مشخصات ساختاریافته سند |
| Document Classification | دسته‌بندی اسناد |
| Version Control | ایجاد و نگهداری نسخه‌های مختلف |
| Workflow | گردش سند برای بررسی و تأیید |
| Review & Approval | تأیید، رد و بازگرداندن سند برای اصلاح |
| Audit Trail | ثبت اقدامات کاربران و تاریخچه تغییرات |
| Search | جستجوی اسناد بر اساس مشخصات و Metadata |
| Basic Dashboard | مشاهده وضعیت اسناد و درخواست‌های در انتظار اقدام |

### 6.3. Features Excluded from MVP

قابلیت‌های زیر می‌توانند در فازهای بعدی توسعه به سامانه اضافه شوند:

- OCR و استخراج خودکار متن از اسناد اسکن‌شده
- Semantic Search (جستجوی معنایی)
- هوش مصنوعی و RAG
- مقایسه خودکار محتوای نسخه‌های مختلف اسناد
- امضای دیجیتال
- اپلیکیشن موبایل
- Workflowهای پیچیده و قابل طراحی توسط کاربران
- اتصال پیشرفته به ERP و سایر سیستم‌های سازمانی
- گزارش‌گیری و تحلیل‌های پیشرفته

## 7. Initial Technical Architecture Proposal

با توجه به نیاز سازمان به میزبانی داخلی (On-Premises)، پیشنهاد اولیه برای فناوری‌های مورد استفاده به شرح زیر است.

> **Important:** موارد زیر پیشنهاد اولیه فنی هستند و انتخاب نهایی فناوری‌ها باید پس از بررسی زیرساخت سازمان، نیازمندی‌های امنیتی، حجم اطلاعات، تعداد کاربران و محدودیت‌های عملیاتی در مرحله Solution Design انجام شود.

| Layer | Proposed Technology | Purpose |
|---|---|---|
| Frontend | React | طراحی رابط کاربری تحت وب |
| Backend | C# / ASP.NET Core Web API | پیاده‌سازی منطق کسب‌وکار و APIها |
| Application Architecture | Clean Architecture | تفکیک مسئولیت‌ها و ساختاردهی نرم‌افزار |
| ORM | Entity Framework Core | ارتباط و مدیریت داده‌های پایگاه داده |
| Database | PostgreSQL | نگهداری اطلاعات اسناد، Metadata و گردش کار |
| File Storage | MinIO (S3-Compatible Object Storage) | نگهداری فایل‌های اصلی اسناد |
| Deployment | Docker | استقرار و مدیریت سرویس‌های سامانه |
| Authentication | Active Directory / LDAP Integration | احراز هویت و یکپارچه‌سازی با کاربران سازمان |
| Advanced Search | OpenSearch | جستجوی پیشرفته در فاز توسعه |

### 7.1. High-Level Architecture

در سطح مفهومی، معماری سامانه به شکل زیر خواهد بود:

```text
                 Organization Users
                         |
                         v
                  Web Application
                     (React)
                         |
                         v
                  Backend API
                 (ASP.NET Core)
                         |
             +-----------+-----------+
             |                       |
             v                       v
       PostgreSQL                 MinIO
       (Metadata)              (File Storage)
             |                       |
             v                       v
       Document Data            Document Files
       Workflow Data            PDF / Word / Excel
       Version Data
       Audit Trail
```

### 7.2. Deployment Considerations

در معماری پیشنهادی:

1. یک زیرساخت اختصاصی برای استقرار سامانه و سرویس‌های موردنیاز در نظر گرفته می‌شود.
2. فایل‌های اصلی اسناد در مخزن مرکزی MinIO ذخیره خواهند شد.
3. اطلاعات مدیریتی، Metadata، نسخه‌ها و گردش کار در PostgreSQL نگهداری می‌شوند.
4. کاربران از طریق رابط وب به سامانه متصل خواهند شد.
5. احراز هویت می‌تواند با Active Directory یا LDAP سازمان یکپارچه شود.
6. ساختار منطقی دسته‌بندی اسناد بر اساس واحد سازمانی، پروژه، نوع و سایر مشخصات موردنیاز طراحی خواهد شد.
7. در صورت افزایش نیازهای جستجو، OpenSearch می‌تواند به معماری اضافه شود.

## 8. Key Business Principles

اصول زیر باید در طراحی و توسعه سامانه رعایت شوند:

| Principle | Description |
|---|---|
| Document Identity | هر سند باید دارای شناسه یا کد یکتا باشد. |
| Version Preservation | هیچ نسخه‌ای نباید با نسخه جدید به‌صورت غیرقابل‌بازگشت جایگزین شود. |
| Controlled Publication | تنها نسخه‌ای که مراحل تأیید موردنیاز را طی کرده باشد، می‌تواند منتشر شود. |
| Document Ownership | هر سند باید مالک یا مسئول مشخص داشته باشد. |
| Traceability | اقدامات مهم کاربران باید در تاریخچه سامانه ثبت شوند. |
| Access Security | مشاهده، ویرایش و تأیید اسناد باید بر اساس سطح دسترسی انجام شود. |
| Approval History | سوابق بررسی، تأیید، رد و اصلاح باید قابل پیگیری باشند. |
| Latest Valid Version | سامانه باید بتواند آخرین نسخه معتبر هر سند را مشخص کند. |
| Archive Preservation | نسخه‌های قدیمی و منسوخ باید با حفظ سوابق نگهداری شوند. |
